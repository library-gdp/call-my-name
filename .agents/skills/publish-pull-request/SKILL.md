# 브랜치·커밋·PR 생성

현재 작업과 저장소 규칙을 보존하면서 브랜치 생성부터 PR 생성까지 순서대로 완료하라.

## 1. 저장소와 변경 사항 확인

1. 저장소 지침 파일과 Git 상태, 현재 브랜치, 변경 diff, 최근 커밋, remote를 확인하라.
2. 현재 세션에서 만든 변경과 기존 사용자 변경을 구분하라. 포함 범위가 불분명하거나 민감정보가 발견되면 커밋하지 말고 사용자에게 확인하라.
3. 커밋할 변경이 없으면 새 브랜치나 빈 커밋, PR을 만들지 말고 그 사실을 보고하라.
4. 기본 브랜치는 `origin/HEAD`를 우선 사용하고, 확인할 수 없을 때만 저장소 설정과 remote branch를 근거로 판단하라.
5. GitHub CLI 등 PR 생성 수단과 인증 상태를 확인하라. 인증 정보는 출력하거나 파일에 기록하지 마라.

## 2. 브랜치 생성

1. 저장소 지침, 기존 브랜치와 최근 이력에서 branch 컨벤션을 확인하고 그 규칙을 우선 적용하라.
2. 명시된 규칙이 없으면 `<type>/<kebab-case-summary>` 형식을 사용하라. 변경 목적에 따라 `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `ci` 중 가장 적합한 type을 선택하라.
3. 브랜치 이름은 실제 변경을 짧고 구체적으로 나타내고, 이미 local 또는 remote에 존재하는 이름과 충돌하지 않는지 확인하라.
4. 기본 브랜치에서 작업 중이면 현재 HEAD와 작업 트리를 보존한 채 새 브랜치를 생성하라. 이미 목적에 맞는 작업 브랜치라면 불필요한 추가 브랜치를 만들지 말고 그 브랜치를 사용하라.
5. detached HEAD, 예상하지 못한 upstream, 기본 브랜치와 무관한 이력처럼 PR 기준을 신뢰할 수 없는 상태라면 임의로 이력을 재작성하지 말고 사용자에게 확인하라.

## 3. 커밋

1. 사용 가능한 `conventional-commit` Skill의 `SKILL.md`를 완전히 읽고 해당 절차에 따라 변경 범위를 검토하고 메시지를 작성해 커밋하라.
2. 현재 작업에 속한 파일만 명시적으로 stage하라. 기존 사용자 변경이나 무관한 untracked 파일을 함께 stage하지 마라.
3. 커밋 후 `git status`와 커밋 내용을 확인하고, 필요한 검증이 실패했으면 원인을 해결하기 전에는 Push하지 마라.

## 4. Push와 PR 생성

1. 새 브랜치를 정상 Push하고 upstream을 설정하라. 강제 Push는 사용자가 명시적으로 요청하고 안전성이 확인된 경우가 아니면 하지 마라.
2. 동일한 head/base 조합의 열린 PR이 이미 있는지 확인하라. 있으면 중복 생성하지 말고 기존 PR을 보고하라.
3. 새 PR의 base는 앞서 확인한 기본 브랜치로 지정하라. 제목은 변경 목적을 간결하게 요약하라.
4. PR 본문에는 다음 내용을 각각 분명한 항목으로 빠짐없이 작성하라.
   - 작업 내용: 실제로 변경한 사항과 주요 구현을 설명하라.
   - 작업 목적: 이 PR로 달성하려는 결과를 설명하라.
   - 작업 이유: 변경이 필요했던 배경과 문제를 설명하라.
   - 검증: 실행한 검사와 결과를 기록하라.
5. placeholder나 사실과 다른 내용을 넣지 말고, diff와 검증 결과에서 확인한 사실만 작성하라.

## 완료 보고

브랜치 이름, 커밋 hash와 메시지, Push 대상, PR 제목과 URL, 검증 결과를 간결하게 보고하라. 완료하지 못한 단계가 있으면 성공한 것처럼 표현하지 말고 실패 지점과 사용자가 취할 다음 조치를 명시하라.
