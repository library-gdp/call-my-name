# 문항별 출력 계약

## 입력 정규화

- 문항은 프롬프트의 번호 목록, 인용문 또는 참조 파일의 제목·번호 목록에서 추출한다.
- 글자 수 제한은 문항에 붙은 표기(예: `500자 이내`, `공백 포함 700자`, `(700자)`)를 우선한다. 공백 포함 여부가 생략된 단일 `N자` 표기는 공백 포함 최대 `N`자로 해석한다. 여러 해석이 가능하면 작성하지 말고 확인한다.
- Job Description은 사용자가 같은 요청에서 제공한 본문 또는 파일만 사용한다. 외부 링크의 공고 본문을 열거나 기존 수집 공고 파일을 참조하지 않는다.

## 완성본 전 사전 점검

- 답변 파일을 만들기 전에 문항이 지원 회사의 선택 이유를 요구하는지, 지원 직무의 선택 이유·희망 업무·직무 적합성을 요구하는지 확인한다.
- 전자에는 지원 회사와 사용자가 제공한 회사 관련 사실·가치 또는 지원 이유가, 후자에는 지원 직무가 필요하다. `USER_INSPECTION.md`에 있는 현재·과거 회사나 담당 직무는 지원 대상이라고 사용자가 확인하지 않은 한 대체 정보가 아니다.
- 필요한 핵심 정보가 하나라도 없으면 모든 답변 파일 생성을 중단하고, 빠진 회사명, 지원 직무, 회사 관련 사실 또는 지원 이유만 간결하게 확인한다. Job Description은 선택 사항이므로 미제공 자체는 중단 사유가 아니다.
- `확인 필요`, `미제공`, 빈칸, 추측한 회사·직무·동기를 답변 본문이나 `작성 확인`에 넣은 파일은 완성본이 아니다. 추가 정보를 받은 뒤 사전 점검을 다시 통과한 문항만 Subagent에 배정한다.

## 파일 형식

각 Subagent는 UTF-8 Markdown 파일 하나를 다음 순서로 작성한다.

```markdown
# 문항 01

## 문항

<사용자가 제공한 문항>

## 답변

<문항 답변 본문>

## 작성 확인

- 글자 수: <N>자 (공백 포함, 제한 <M>자 이내)
- 사용자 컨텍스트 근거: <EXP-* ID 또는 확인 가능한 사실>
- Job Description 반영: 예 | 아니오
```

- 파일명은 `question-01.md`, `question-02.md`처럼 문항의 입력 순서를 두 자리로 표기한다.
- 답변 본문만 글자 수 제한의 대상이다. 공백 포함 여부가 사용자가 따로 정한 경우 그 기준을 따른다.
- 사용자 컨텍스트 근거에는 `USER_INSPECTION.md`에 존재하는 경험 ID나 사실만 적는다. 근거가 부족해 문항의 핵심에 답할 수 없으면 답변을 꾸미거나 `확인 필요` 파일을 만들지 말고 사용자 확인 단계로 돌아간다.

## 작성 품질 점검

- 사용자가 요청한 언어로 작성한다. 언어가 명시되지 않으면 요청과 문항의 주된 언어를 따르고, 서로 다르거나 모호하면 작성 전에 확인한다.
- 문항이 요구하는 주제에 첫 문장부터 답한다.
- 가능한 한 사용자의 검증 가능한 경험을 중심으로 상황·행동·결과를 구체적으로 쓰고, 경험과 문항의 연결을 명확히 한다.
- Job Description이 있을 때만 관련 경험을 연결하고, 키워드 나열로 대체하지 않는다.
- 사실성과 가독성을 해치지 않는 범위에서 제한 최대치에 최대한 가깝게 작성한다. 근거가 충분한 상황·행동·결과를 구체화하되 반복·과장·창작으로 분량을 채우지 않는다.
- 제한을 초과하면 불필요한 수식·반복·일반론부터 줄이고, 사실과 인과관계를 훼손하지 않는다.
- 문항 간 같은 경험의 반복은 가능한 피한다. 반복이 불가피하면 문항별 관점을 달리하고 그 사실을 상위 Agent에 알린다.
