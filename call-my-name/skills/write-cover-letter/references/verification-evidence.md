# 검증 실행 증거 보존

이 문서는 개발·테스트 환경에서 `write-cover-letter`의 실제 수행을 독립 검증할 때만 적용한다. 사용자 답변이나 사용자 컨텍스트 원문, 개인정보, 인증정보를 기록하지 않는다.

## 문항별 담당자와 직접 작성

1. 실행 전에 테스트 하네스는 문항 번호, Subagent ID, 배정 출력 경로만 담은 `dispatch.jsonl`을 보존한다.
2. 플랫폼이 남기는 원본 `spawn_agent`, 각 담당자의 파일 작성 도구 호출, 같은 담당자에 대한 `followup_task` 수정 호출을 문항별 원본 이벤트 파일로 내보낸다. 이벤트에는 ID·시각·도구명·허용 출력 경로만 남기고 문항 본문과 사용자 컨텍스트는 제거하거나 해시로 대체한다.
3. `question-XX.md`의 최초 작성과 모든 수정은 배정된 같은 Subagent ID의 이벤트와 대응해야 한다. 상위 Agent나 다른 Subagent의 해당 파일 쓰기 이벤트가 하나라도 있으면 실패다.
4. 사람이 만든 요약 표나 사후 보고서는 원본 이벤트 파일의 경로와 해시를 가리킬 수만 있으며, 원본 기록을 대신할 수 없다.

## 외부 공고 미사용 음성 검증

1. 격리 작업공간의 `src/jobs/`와 `__workspace__/agent/jobs/`에 서로 다른 고유 미끼 토큰이 들어 있는 파일을 만든다. 이 파일을 Subagent 입력으로 전달하지 않는다.
2. 원본 실행 이벤트에서 두 금지 경로의 읽기, `$collect-job` 호출, 웹·외부 공고 조회가 모두 0건인지 검사한다. 미끼 파일을 만드는 준비 작업은 별도 단계로 표시한다.
3. 각 Subagent에 전달한 정규화 입력과 최종 `question-*.md`에서 두 토큰을 검색해 0건인지 기록한다.
4. 원본 이벤트 파일, 토큰 검사 결과, 출력 파일 SHA-256을 격리 실행 디렉터리에 보존한다. 테스트 보고서는 이 경로·해시·검사 명령을 인용하며 성공을 재서술만 하지 않는다.

## 회귀 시나리오

- 파일 입력·복수 문항·JD 미제공: JD 반영 표기가 `아니오`이고, 필요한 회사·지원 직무가 빠진 문항은 파일보다 사용자 확인이 먼저여야 한다.
- 프롬프트 입력·단일 문항: 동일한 사전 점검과 한 개의 Subagent/한 개의 파일 계약을 확인한다.
- 사용자 제공 JD 포함: 외부 공고를 읽지 않고 그 JD만 반영하며 `Job Description 반영: 예`를 확인한다.
