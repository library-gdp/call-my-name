# 채용공고 수집

`src/JOB_SEEKER.md`의 사용자 지정 기업과 공개 URL을 대상으로, 공식 채용 페이지를 우선하여 현재 접근 가능한 채용공고 원문을 수집하라. 공고 원문은 요약·의역하지 않고 보존하며, 비본문 UI와 기술 데이터만 제거하라.

## 입력과 출력 경로

- 실행 작업공간 루트를 기준으로 입력은 `src/JOB_SEEKER.md`, 공고 출력은 `__workspace__/agent/jobs/`로 고정한다. `src/jobs/JOB_SEEKER.md` 등 다른 경로를 추측하거나 읽지 마라.
- 입력은 URL만, 기업 목록만, 또는 둘 모두를 포함할 수 있다. URL은 Markdown 링크 또는 `http://`·`https://` 원문 URL로 등장 순서대로 읽는다. 같은 URL과 fragment 또는 공고 식별에 필요하지 않은 추적 파라미터만 다른 URL은 한 번만 처리하되, 식별 쿼리는 유지한다. URL별 정규화·재시도·증거 기록 방법은 참조 계약을 따른다.
- 기업 목록은 `## 조사 대상 기업` 또는 `## 기업` 아래의 목록, `기업명:` 필드, 또는 URL이 아닌 명시적 목록 항목에서 읽는다. 관심 직무·근무지·고용 형태·경력 구분은 `## 선별 조건` 아래 또는 해당 이름의 필드에서만 읽고 후보 선별에만 사용한다. 공고 본문·조건·기업명이 아닌 일반 설명문은 추측해 대상에 넣지 마라.
- 기업명 동명이인, 법인명·브랜드명 관계, URL의 기업 귀속이 불명확하면 공식 도메인·공식 채용 페이지에 표시된 명칭 같은 공개 식별 근거가 확보될 때까지 단정하지 말고 `확인 불가`와 후속 확인으로 남겨라.
- 입력 파일이 없거나 읽을 수 있는 URL·기업이 모두 없으면 공고 파일을 만들거나 바꾸지 말고, 필요한 경로 또는 입력 형식을 사용자에게 알린다. 형식 오류가 있는 줄은 무시하여 추측하지 말고 완료 보고에 기록한다.

수집 전에 [references/extraction-contract.md](references/extraction-contract.md)를 처음부터 끝까지 읽고, 후보·원문·증거·파일·보고 계약을 모두 적용하라.

## 수집 절차

1. URL 입력마다 **식별 쿼리를 보존해 정규화한 공개 URL을 먼저 계산하고 기록한 뒤**, 그 URL을 첫 브라우저 열기 대상으로 사용한다. fragment와 입증된 비식별 추적 파라미터만 제거한다. 안전 정책이 거부하거나 열기가 실패하면 같은 origin/path에서 공고 식별 쿼리만 남긴 최소 정규 공개 URL을 반드시 한 번 더 열고, 두 URL·제거/보존 파라미터·결과를 증거에 남긴다. 로그인, CAPTCHA, `robots.txt`, 이용약관과 접근 제한은 우회하지 마라.
2. 사용자가 제공한 기업과 URL만 조사 대상으로 삼는다. 기업별로 공식 도메인과 공식 채용 페이지를 먼저 찾고, 확인한 기업 식별 근거와 공식 여부를 기록한다. URL이 있더라도 기업 귀속과 공식 기준본 존재를 확인한다.
3. 공식 페이지에서 현재 접근 가능한 후보를 찾고, 제공된 선별 조건에 맞는지 원문 근거로 판정한다. 조건을 만족하지 않거나 이미 마감된 후보는 삭제하지 말고 후보·제외 사유·원문 상태를 완료 보고와 증거에 남긴다. 조건이 없는 경우에는 발견한 현재 접근 가능 후보를 임의의 추가 조건으로 제외하지 마라.
4. 공식 기준본을 찾을 수 없거나 직접 참조된 원문을 보강해야 할 때에만 공개 채용 플랫폼과 공식 페이지가 직접 가리키는 공개 첨부 문서를 보조 출처로 사용한다. 검색 결과 snippet, 다른 기업의 일반 페이지, 추측한 API는 원문으로 쓰지 마라.
5. 동일·실질 동일 공고는 기업 식별, 공고명, 직무·근무지, 날짜 등 공개 근거로 식별한다. 공식 원문을 기준본으로 우선하되, 출처별 본문이 다르면 합성·보정·판정하지 말고 각 원문과 차이 존재를 구분해 보존한다.
6. 정규 공개 URL과 redirect 최종 공개 URL의 브라우저 렌더링 영역을 확인한 뒤 JSON-LD·공개 초기 상태·페이지가 직접 사용하는 인증 없는 공개 데이터·공개 iframe·이미지·PDF·첨부 문서를 차례대로 대조한다. 3xx, 빈 HTML shell 또는 JavaScript 안내만으로 실패 처리하지 마라.
7. 요약 카드·목록과 상세 본문이 함께 있으면 요약 카드만으로 완료하지 마라. 상세 리소스의 시작부터 끝까지 섹션 인벤토리를 만들고, 모든 공개 하위 리소스까지 대조하여 담당 업무, 자격·우대, 고용·근무 조건, 전형·일정, 제출·지원 방법, 복리후생, 유의·법적 고지, 각주·예외·수습·계약 조건, 문의처를 포함했는지 확인한다. 상세 리소스 안의 회사·사업 소개는 사이트 공통 UI임이 공개 근거로 입증되지 않으면 보존한다.
8. 후보별 기업명, 공고명, 정규 원문 URL, 게시·수정·마감 정보 및 수집 시점의 모집 상태를 공개 근거로 확인한다. 렌더링 영역, JSON-LD, 공개 초기 상태를 순서대로 대조하고, 출력 메타데이터의 각 필드에 실제 확인한 근거를 연결한다. 확인하지 못한 값만 `확인 불가`로 쓴다.
9. 원문 문구·수치·순서·제목 계층·문단·목록·표의 행열 대응·의미 있는 굵게·밑줄·강조 범위를 보존한다. 이미지에서 읽을 수 있는 공고 문구는 빠짐없이 전사하고 이미지 기반 전사임을 밝힌다. 구조 또는 강조 범위를 Markdown으로 보존할 수 없으면 원문 구조·범위와 `확인 필요` 사유를 주석으로 남긴다.
10. HTML·CSS·JavaScript, SEO·추적·세션·내부 식별자, 사이트 공통 UI, 광고·추천, 로그인·앱 설치·쿠키 안내, 공유·조회 지표처럼 모집 내용이 아닌 것만 제거한다. 상세 리소스에서 의도적으로 제거한 블록은 공통 UI임을 입증한 근거와 함께 증거에 남긴다. 불필요한지 확실하지 않거나 지원 판단에 영향을 줄 수 있으면 보존한다.
11. 공고와 대조 증거를 완성한 뒤에만 `__workspace__/agent/jobs/`에 저장한다. 임시 파일을 거쳐 원자적으로 교체하고, 같은 정규 원문 URL의 같은 공고를 재실행하면 새 번호 파일을 만들지 말고 기존 파일을 교체한다. 이름이 다른 공고와 충돌할 때만 계약의 충돌 규칙을 적용한다.
12. 모든 공개 확인 경로를 거친 뒤에도 공고명과 모집 본문을 신뢰할 수 없을 때만 해당 공고 파일을 만들지 말고, 확인한 경로·각 결과·실패 이유를 증거와 완료 보고에 남긴 뒤 나머지 대상을 계속 처리한다.

## 완료 점검

- 성공 공고마다 계약에 맞는 파일이 하나씩 있고, 원문 URL·출처명·출처 유형·수집 시각·확인된 게시·수정·마감일·모집 상태가 근거와 일치하는지 확인한다.
- 첫 브라우저 열기 전에 정규 URL을 계산했고, 안전 정책 거부·실패 시 같은 origin/path의 최소 정규 공개 URL을 재시도했는지 증거에서 확인한다. 제거·보존 쿼리와 그 이유가 후보별로 남아 있어야 한다.
- 렌더링 본문, JSON-LD, 공개 초기 상태, iframe, 이미지, PDF·첨부 문서와 상세 본문을 각각 확인했는지 증거에서 대조한다. 비어 있거나 적용되지 않는 표면도 그 사실과 근거를 남긴다.
- 상세 리소스의 시작~끝 섹션 인벤토리, 보존 위치, 의도적으로 제거한 블록과 공통 UI 근거가 증거에 있는지 확인한다. 회사·사업 소개를 근거 없이 제거하지 않는다.
- 상세 표의 모든 헤더·행·셀, 목록, 제목 계층, 각주·예외·법적 고지와 굵게·밑줄 범위가 원문 순서와 관계를 유지하는지 대조한다. 요약 카드만 남고 상세 내용이 누락되지 않았는지 확인한다.
- 제거한 내용이 모집 내용이 아닌 UI·기술 데이터뿐이며, 날짜·상태·경력·자격·급여·절차를 만들거나 원문을 요약·재작성하지 않았는지 확인한다.
- 완료 보고에는 기업별 성공 여부·발견 공고 수·공식/보조 출처 판단, 성공 파일, 제외 후보와 사유, 마감·상태 불명, 출처 충돌·접근 제한·입력 오류·후속 확인을 계약의 표로 제시한다. 재실행·파일명 충돌 처리 결과와 증거 경로도 포함한다.
- 격리 회귀를 수행할 때는 계약의 모든 필수 분기에 대해 입력·공개 근거 또는 고정 fixture·정규 URL·실행 전후 파일 목록과 해시·선택 파일·임시 파일 원자 교체 결과를 후보별 증거로 남긴다. 잡코리아와 사람인 회귀 실패 조건도 적용한다.
