# 채용공고 원문·증거·보고 계약

## 1. 대상·후보·출처 계약

1. 입력에서 명시된 기업과 URL만 조사한다. 기업 목록만 있어도 공식 채용 페이지 탐색을 수행하며, URL만 있어도 URL의 기업 귀속과 공식 기준본을 확인한다.
2. 기업 식별은 공식 도메인, 공식 채용 페이지의 기업명, 제공 URL의 기업 표기 같은 공개 근거로 한다. 같은 이름의 다른 법인·브랜드일 수 있으면 근거 없이 합치지 않는다.
3. 기업별 공식 채용 페이지를 먼저 탐색한다. 공식 페이지의 현재 공고를 기준본으로 하며, 공식 페이지를 찾지 못했거나 공식 페이지가 직접 연결한 자료를 확인할 때만 공개 채용 플랫폼·공개 첨부 문서를 보조 출처로 쓴다.
4. 관심 직무·근무지·고용 형태·경력 구분 등 사용자가 제공한 조건은 후보 선별에만 사용한다. 각 일치·제외 판정에는 해당 원문의 문구 또는 `확인 불가` 근거가 필요하다. 사용자가 주지 않은 조건을 추가하지 않는다.
5. 동일 공고는 공개 기업 식별 근거와 공고명, 직무·근무지, 날짜 등을 대조해 판단한다. 공식·보조 출처의 본문이 다르면 한 문서로 섞거나 차이를 의역하지 않는다. 기준본과 각 보조 원문을 분리하고 `본문 차이 있음 — 통합하지 않음`을 기록한다.

## 2. URL 정규화와 공개 페이지 확인 순서

각 후보와 각 사용 URL에 아래 확인을 모두 수행한다. 한 단계가 빈 결과이거나 실패해도 다음 공개 단계를 건너뛰지 않는다.

1. **첫 브라우저 열기 전** 입력 URL에서 fragment를 제거하고, 공고 식별에 필요하지 않음이 입증된 추적 파라미터만 제거해 정규 공개 URL을 계산한다. `rec_idx`, `job_id`, `position`, 공고 식별 경로처럼 해당 공고를 가리키는 쿼리·경로는 보존한다. `utm_*`, `gclid`, `fbclid`, `t_ref`, `t_ref_content`, `t_ref_area`처럼 추적임이 명확한 값만 제거할 수 있으며, 알 수 없는 쿼리는 추적이라고 추정해 제거하지 않는다. `view_type` 등 화면 제어 값도 제거하려면 해당 사이트에서 공고 식별에 필요 없다는 공개 근거를 남긴다.
2. 이 정규 공개 URL을 첫 브라우저 열기 대상으로 사용하고, redirect 최종 공개 URL과 함께 렌더링 영역의 공고명·기업명·본문·상태를 확인한다. 안전 정책 거부 또는 열기 실패면 같은 origin/path에서 식별 쿼리만 남긴 **최소 정규 공개 URL**을 계산하여 반드시 다시 연다. 최초 URL·첫 정규 URL·재시도 URL이 같아도 재시도 호출과 결과를 기록한다. 다른 도메인·추측 경로·비공개 API로 바꾸지 않는다.
3. HTML의 JSON-LD를 확인한다. `datePosted`, `validThrough`, 기업명, 고용 형태 등 공개 필드는 렌더링 영역과 대조한다.
4. 페이지가 제공하는 공개 초기 상태 데이터를 확인한다. 화면 렌더링 전용 기술 데이터는 원문 본문에 넣지 않지만, 실제 공고 메타데이터의 근거로만 사용한다.
5. 페이지가 직접 사용하는 인증 없는 공개 데이터 요청이 있으면, 그 요청이 실제 페이지의 공고를 가리키는지 확인한 뒤 확인한다. 비공개 API를 추측하거나 인증·우회 수단을 쓰지 않는다.
6. 페이지와 공개 하위 문서의 `iframe`을 모두 확인한다. 중첩 iframe도 실제 공고 본문을 포함하면 같은 순서로 확인한다.
7. 공개 이미지, PDF, 첨부 문서와 상세 본문으로 가는 직접 링크를 확인한다. 이미지·PDF의 읽을 수 있는 공고 문구, 표, 각주, 법적 고지를 전사한다. 판독할 수 없는 부분은 추측하지 않고 위치와 `확인 필요`를 남긴다.
8. 요약 카드·목록과 상세 본문이 공존하면 다음 체크리스트로 대조한다. 상세 표나 목록을 요약 카드로 대체하지 않는다.

| 대조 대상 | 확인 기준 |
| --- | --- |
| 제목·기업·모집분야 | 본문과 메타데이터가 실제 같은 공고를 가리킨다. |
| 담당 업무·역할 | 상세 문장과 하위 목록을 전부 보존한다. |
| 자격·우대 | 표의 헤더와 각 행·셀 대응, 조건·예외를 보존한다. |
| 고용·근무 조건 | 고용형태, 수습·계약, 경력·학력, 급여, 시간, 근무지, 인원을 빠뜨리지 않는다. |
| 전형·일정·지원 | 전형 순서, 제출 서류, 지원 방법, 게시·수정·마감 표현을 보존한다. |
| 복리후생·문의 | 공고별 제공 내용과 공식 문의처를 보존한다. |
| 유의·법적 고지 | 허위 기재, 중복 지원, 장애인·보훈, 조기 마감, 취소, 예외·각주를 보존한다. |

3xx, 빈 shell, JavaScript 안내, `curl` 본문 없음, 첫 URL의 안전 정책 거부는 실패의 단독 근거가 아니다. 정규 URL의 첫 열기와 같은 origin/path 최소 정규 URL 재시도를 포함한 위 단계를 확인한 후에만 `본문 없음`, `접근 차단`, `로그인 필요`, `이미지 판독 불가` 등 실제 이유로 판정한다.

## 3. 원문 보존·제거 계약

포함 대상은 모집공고명·기업명, 접수일, 모집분야·직무, 담당 업무, 지원·필수·우대 요건, 근무지, 경력·학력, 전형·일정, 제출·지원 방법, 복리후생, 보상·수당, 고용형태·근무시간·계약기간·근무방식, 문의처와 지원 판단에 영향을 주는 모든 문구다.

- 출처의 문장·항목명·수치·오탈자를 그대로 옮긴다. 축약, 바꿔쓰기, 문체 통일, 교정, 번역, 재분류, 누락값 보완을 하지 않는다.
- 제목·단락·목록·표의 행열 관계·본문 순서와 의미 있는 굵게·밑줄·강조를 가능한 한 유지한다. Markdown 표로 관계를 보존할 수 없으면 원래 행·열 관계를 설명하고 `확인 필요` 주석을 남긴다.
- 상세 페이지·iframe·PDF 등 **공고 상세 리소스 내부**의 시작부터 끝까지 제목, 문단, 표, 목록, 이미지/첨부, 각주와 고지의 순서 인벤토리를 만든다. 회사 연혁·사업·서비스·팀 소개는 지원 판단에 쓸 수 있는 상세 본문이며, 다른 공고에서도 동일한 사이트 공통 UI임을 URL·반복 위치 등 공개 근거로 입증하지 못하면 보존한다.
- 상세 리소스에서 제거하는 블록은 인벤토리에 `제거`로 표시하고, 블록의 시작·끝 또는 식별 문구, 제거 사유, 공통 UI임을 입증한 공개 근거를 남긴다. 근거가 없으면 제거하지 않는다.
- 원문과 출력의 모든 표·목록·문단을 대조할 때 굵게(`strong`/`b`)·밑줄(`u`)·기타 의미 있는 강조의 **정확한 시작·끝 텍스트 범위**까지 비교한다. 한 셀의 일부만 굵은 원문을 더 넓히거나, 셀 전체가 굵은 원문을 일부만 굵게 만들지 않는다. Markdown 표현이 불가능하면 원문 범위와 보존 불가 이유를 `확인 필요`로 기록하고 부분 보존을 완료로 판정하지 않는다.
- 반복이 사이트 UI 때문에 생긴 것이 확실할 때만 중복을 제거한다. 공고 본문의 의도적 반복, 각주, 예외, 법적 고지, 수습·계약 조건은 보존한다.
- 이미지 기반 문구는 원문대로 전사하고 출처 검증 정보에 `- 이미지 기반 전사: <이미지 URL 또는 위치>`를 추가한다.
- 다음만 제거한다: HTML 태그·CSS·JavaScript·추적 코드·세션·내부 ID, 전역 header/footer/navigation·cookie·로그인 UI, 직무 정보 없는 일반 홍보, 모집 내용과 무관한 전역 개인정보처리방침, 조회·공유·앱 설치·추천 공고·다른 공고 링크. 상세 리소스 내부에서는 공통 UI임이 입증된 경우에만 해당한다. 불필요한지 불확실하면 보존한다.

## 4. 메타데이터와 원문 파일 계약

각 성공 공고는 한 Markdown 파일로 저장한다. 공식·보조 출처가 같은 공고의 서로 다른 본문을 제공하면 기준본과 보조 원문을 파일 안에서 출처별로 분리한다.

```markdown
# <출처의 모집공고명>

## 출처 검증 정보

- 기업명: <출처에 표시된 기업명 또는 확인 불가>
- 출처명: <공고를 게시한 사이트 또는 기업 채용 페이지명 또는 확인 불가>
- 출처 유형: <공식 채용 페이지 | 공개 채용 플랫폼 | 공개 첨부 문서 | 확인 불가>
- 원문 URL: <실제 공고를 가리키는 정규 공개 URL>
- 수집 시각: YYYY-MM-DDTHH:MM:SS±HH:MM
- 게시일: <출처 원문 또는 확인 불가>
- 수정일: <출처 원문 또는 확인 불가>
- 마감일: <출처 원문 또는 확인 불가>
- 모집 상태: <출처 원문 또는 확인 불가>

## 정제한 공고 원문

<공고 원문의 제목·단락·목록·표를 출처 순서대로 기록>
```

- 게시일·수정일·마감일·모집 상태는 렌더링 영역, JSON-LD, 공개 초기 상태를 순서대로 대조해 실제 확인한 값을 원문 표현대로 쓴다. 어느 표면에서 확인했는지는 증거 파일에 연결한다. 모든 표면에서 확인하지 못한 값만 `확인 불가`다.
- `상시채용`, `채용 시 마감` 등은 날짜로 바꾸지 않는다. 해석할 때만 `- 상태 해석: <해석>`을 추가하고 원문 표현을 대체하지 않는다.
- `수집 시각`의 날짜는 파일명의 날짜와 같다. 파일명은 `<SHORT_POSTING_TITLE>_<YYYY_MM_DD>.md`로 하고, 공백·구분 문자는 `_`, 영문은 대문자로 바꾼다. 한글·숫자는 유지하며 경로 구분자·제어 문자·안전하지 않은 문자는 제거한다.
- 다른 공고가 같은 파일명과 충돌하면 공고명 뒤에 기업명을 붙이고, 그래도 충돌하면 `_2`, `_3`을 붙인다. 동일 정규 원문 URL과 동일 공고를 같은 날 재실행하면 기존 대상 파일을 임시 파일로 완성한 뒤 원자적으로 교체한다.
- 원문 URL은 최종 공개 공고 URL을 쓴다. fragment와 공고 식별에 필요하지 않은 추적 파라미터만 제거하며, 식별 경로·쿼리는 보존한다. 공개 대체 원문을 쓰면 원 URL과의 관계를 완료 보고에 남긴다.
- 출처별 본문이 다르면 `## 출처 간 확인 메모`를 원문 앞에 넣고, 출처명·URL 및 `본문 차이 있음 — 통합하지 않음`을 기록한다. 각 본문은 `### <출처명> 원문` 아래 원문 순서대로 보존한다.
- 공고 파일에는 접근 오류 자체를 넣지 않는다. 다만 구조 보존 불가의 `확인 필요`와 이미지 기반 전사는 출처 검증 주석으로 남긴다.

## 5. 증거 보존 계약

성공·제외·상태 불명 후보마다 `__workspace__/agent/jobs/.evidence/`에 대조 기록을 보존한다. 원문 HTML 전체나 비본문 UI를 복사하지 않고, 재검증 가능한 공개 URL·확인 시각·정확한 섹션명·출력 위치·판정 근거를 남긴다.

```markdown
# 수집 대조 증거 — <기업명 또는 입력 URL>

- 입력 대상: <기업명 또는 URL>
- 확인 시각: YYYY-MM-DDTHH:MM:SS±HH:MM
- 입력 URL: <원문 URL 또는 해당 없음>
- 첫 열기 정규 URL: <fragment·입증된 비식별 추적값만 제거한 URL 또는 해당 없음>
- 최소 정규 재시도 URL: <같은 origin/path와 식별 쿼리만 남긴 URL 또는 재시도 불필요>
- 제거한 URL 요소: <fragment·파라미터명=값과 비식별/추적 근거, 없으면 없음>
- 보존한 식별 요소: <경로·파라미터명=값과 공고 식별 근거, 없으면 없음>
- URL 열기 결과: <첫 열기와 안전 정책 거부 시 재시도의 각각의 결과>
- 기업 식별 근거: <공식 도메인/공식 페이지 표기/확인 불가>
- 후보: <공고명 또는 확인 불가>
- 판정: <성공 | 제외 | 상태 불명 | 접근 불가 | 확인 불가>
- 공고 파일: <성공 시 상대 경로, 그 외 없음>

| 확인 표면 | 공개 URL 또는 위치 | 확인한 원문 섹션·필드 | 출력 위치 또는 제외 근거 |
| --- | --- | --- | --- |
| 렌더링 영역 | ... | ... | ... |
| JSON-LD | ... | `datePosted` 등 또는 없음 | 메타데이터 필드 |
| 공개 초기 상태 | ... | ... 또는 없음 | ... |
| 공개 데이터 | ... | ... 또는 적용 없음 | ... |
| iframe | ... | ... 또는 없음 | ... |
| 이미지/PDF/첨부 | ... | ... 또는 없음 | ... |
| 상세 본문 대조 | ... | 체크리스트 각 항목 | 공고 원문의 제목/표/목록 |
```

- `확인 불가`, 제외, 실패도 위 표에 실제 시도한 공개 표면과 결과를 기록한다. 3xx·빈 shell만 기록하고 실패로 끝내지 않는다.
- `상세 본문 대조`에는 다음 두 표를 추가한다. 상세 리소스가 없으면 그 근거를 각 표에 남긴다.

```markdown
### 상세 리소스 섹션 인벤토리

| 순서 | 리소스 URL 또는 위치 | 원문 블록 종류·제목/첫 문구 | 보존 위치 | 판정 |
| ---: | --- | --- | --- | --- |
| 1 | ... | 문단 · `...` | 공고 원문 ... | 보존 |
| 2 | ... | 표 · `...` | 공고 원문 ... | 보존 |

### 의도적으로 제거한 상세 리소스 블록

| 리소스 URL 또는 위치 | 블록 시작·끝 또는 식별 문구 | 제거 사유 | 공통 UI임을 입증한 공개 근거 |
| --- | --- | --- | --- |
| 없음 또는 ... | ... | ... | ... |

### 구조·강조 범위 대조

| 원문 위치 | 원문 구조 또는 강조 범위 | 출력 위치·표현 | 판정/확인 필요 사유 |
| --- | --- | --- | --- |
| 표 1행 1열 | `strong`: `JAVA 개발 및 운영` 전체 | 공고 원문 표 1행 1열: `**JAVA 개발 및 운영**` | 일치 |
```

- 제거 표에서 `없음`은 상세 리소스 전체를 인벤토리와 출력에 대조한 뒤에만 쓴다. 회사·사업 소개가 빠진 경우에는 `공통 UI임을 입증한 공개 근거` 없이 `제거`로 기록하거나 완료로 판정하지 못한다.
- 메타데이터의 각 확인 값은 표의 출처 표면과 원문 필드를 연결한다. 모집 상태는 수집 시각에 확인한 원문 상태·마감 문구·상태 UI의 근거를 남기며, 근거가 없으면 `확인 불가`다.
- 파일명 충돌이면 선택한 충돌 해소 이름과 기존 파일의 정규 원문 URL 대조 결과를 남긴다. 재실행이면 기존 파일 교체 여부를 남긴다. 격리 회귀 실행이면 아래 파일 안전성 기록도 후보별 증거에 추가한다.

```markdown
### 파일 안전성·회귀 실행 기록

- 시나리오: <중복 | 재실행 | 파일명 충돌 | 입력 오류 | 기타>
- 격리 입력: <경로>
- 입력 SHA-256: <해시>
- 공개 근거 또는 고정 fixture: <공개 URL·확인 시각 또는 fixture 경로·출처·SHA-256>
- 정규 URL 계산: <입력 URL → 첫 열기 정규 URL → 최소 재시도 URL>
- 실행 전 파일 목록·SHA-256: <경로와 해시 또는 비어 있음>
- 선택 파일과 선택 근거: <동일 정규 URL 기존 파일 / 충돌 파일 / 새 파일>
- 임시 파일: <같은 디렉터리의 임시 경로·SHA-256·완성 확인>
- 원자 교체: <임시 파일 → 대상 파일, 성공/실패, 교체 후 임시 파일 없음 여부>
- 실행 후 파일 목록·SHA-256: <경로와 해시>
```

## 6. 완료 보고 계약

실행 종료 시 아래 형식으로 기업별 결과를 제시한다. URL만 입력된 경우에도 식별한 기업명 또는 `확인 불가`를 한 행으로 사용한다.

| 기업 | 식별 근거·출처 우선 판단 | 발견 공고 수 | 성공 파일 | 제외 후보·사유 | 마감/상태 불명 | 충돌·접근 제한·후속 확인 | 증거 |
| --- | --- | ---: | --- | --- | --- | --- | --- |
| ... | 공식 기준본 / 보조 출처 사유 / 확인 불가 | 0 | ... | ... | ... | ... | ... |

마지막으로 입력 오류, URL 중복 제거, 동일 URL 재실행 교체, 파일명 충돌 처리 여부를 별도로 적는다. 일부 실패가 있어도 다른 기업·URL 처리를 중단하지 않는다.

## 7. 격리 회귀 검증 계약

Skill 변경을 검증하거나 재현할 때 원본 `src/JOB_SEEKER.md`와 사용자가 준 입력을 수정하지 않는다. 각 시나리오는 별도 격리 작업공간과 복사한 입력으로 실행하고, 후보별 `.evidence`에 5절의 파일 안전성·회귀 실행 기록을 빠짐없이 남긴다.

- 공개 채용 사실은 실제로 현재 또는 고정 시점에 공개 확인한 URL만 사용한다. 네트워크 상태가 바뀌어도 재현해야 하는 경우에는 저장소 개발 영역의 비개인·고정 fixture를 사용하되, 원본 URL·확인 시각·원문 보존 범위·SHA-256을 기록한다. fixture의 공고명·기업·본문·이미지/PDF 문구를 지어내거나 수정하지 않는다.
- 빈 입력·지원하지 않는 형식·깨진 URL 검증에는 공고 사실을 포함하지 않는 구조 전용 입력을 만들 수 있다. 공고 파일이 추가·교체되지 않았다는 실행 전후 목록과 해시를 남긴다.
- 아래 분기는 모두 독립적으로 검증한다. 하나의 실제 공고에서 증명할 수 없는 분기는 공개 근거가 있는 다른 실제 사례 또는 위 고정 fixture를 쓴다.

| 필수 격리 시나리오 | 최소 긍정 증거 |
| --- | --- |
| 기업-only와 선별 조건 | 기업명·조건만 든 복사 입력, 공식 채용 페이지를 먼저 확인한 URL, 후보별 조건 일치/제외 원문 근거 |
| 공식/보조 출처 충돌 | 같은 공고의 공개 공식·보조 원문 URL, 각 본문을 합성하지 않고 분리한 파일과 `본문 차이 있음 — 통합하지 않음` |
| 이미지 또는 PDF | 읽을 수 있는 실제 이미지/PDF의 문구·표·각주 전사 또는 판독 불가 위치와 근거 |
| 다른 공고의 파일명 충돌 | 서로 다른 정규 URL·공고임을 보이는 두 후보, 선택한 기업명/번호 접미 파일과 양쪽 URL 대조 |
| 빈/형식 오류 입력 | 격리 입력·입력 해시, 공고 파일을 만들거나 바꾸지 않은 전후 목록·해시 |
| 추적 URL·fragment 중복 | 원본과 추적/fragment 변형 입력, 두 정규 URL 계산, 한 번만 선택된 공고 파일 |
| 동일 URL 재실행 | 기존 파일의 정규 URL, 같은 디렉터리 임시 파일 해시, 원자 교체 전후 목록·해시와 임시 파일 제거 |

### 완료 전 고정 회귀 체크리스트와 실패 조건

다음은 선택 사항이 아니다. 어느 하나라도 증거·출력에서 확인되지 않으면 해당 실행을 완료 또는 원문 무손실 보존 성공으로 보고하지 말고, `확인 불가` 또는 실패 사유와 후속 확인을 남긴다.

- **잡코리아 `GI_Read/49649371` 사례를 사용한 경우:** 공개 상세 iframe의 시작부터 끝까지 인벤토리를 만들고, `artTopDesc`의 회사·사업 소개, `포지션 및 자격요건` 4열 표, 복리후생, 전형절차, 근무조건, 유의사항을 출력과 대조한다. 첫 표 셀의 `JAVA 개발 및 운영` 전체 굵게 범위와 원문의 밑줄·굵게 범위도 대조한다. 회사 소개 누락, 공통 UI 근거 없는 제거, 표·법적 고지 누락, 강조 범위 불일치는 실패다.
- **사람인 `rec_idx=54409602` 사례를 사용한 경우:** fragment·`t_ref*` 등 제거값과 `rec_idx=54409602` 보존값을 증거에 기록하고, 첫 브라우저 열기 전에 계산한 정규 URL 및 안전 정책 거부 시 같은 origin/path 최소 정규 URL 재시도를 실제로 수행한다. 재시도 URL·열기 결과·확인한 기업/공고/본문 표면 또는 접근 제한의 구체 근거가 없으면 실패다. 최초 긴 URL의 307 또는 안전 정책 거부만으로 `확인 불가`를 완료 처리해서는 안 된다.
